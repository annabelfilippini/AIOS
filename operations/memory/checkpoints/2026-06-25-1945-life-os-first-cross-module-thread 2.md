# Session: Life OS — first cross-module thread (The Day -> The Edit)

## What shipped (builds on Batch 1 SPA shell)
The calendar -> wardrobe chain from the README is real and working on her live
Google Calendar:
1. The Day classifies each event's **occasion** from its title (`occasionOf`):
   Airport->vacation, Strength->active, dinner/drinks->going-out, meeting/
   webflow->work, coffee/lunch->casual; admin/home (laundry, "call mum")-> null.
2. Events with a real outfit decision get a faint **✦ wear button** in `.rowacts`.
3. Click -> `window.LifeOS.goToEdit(occasion, ctx)` -> switch to The Edit, apply
   that occasion filter, drop a context banner "FROM THE DAY · DRESSING FOR /
   {title} · {time}".
4. Banner **×** (or any occasion chip clicked by the user) clears context back to
   All. Verified end-to-end: Airport->vacation showed 56 pieces; clear reset to 328.

## How it's wired (the deliberate architecture)
- **The Edit (`feed.html`) was NOT touched** — it's generated by build_feed.py, so
  editing it would rot. The shell filters The Edit *through its own occbar chips*
  (`chip.click()`). The chips ARE the API. Banner injected into #view-edit by shell.
- **The Day (`planner.html`)** got: `occasionOf()` classifier, a wear button in the
  timeline row (only rendered when `window.LifeOS` exists -> standalone shows none),
  and the click handler. Backward-compatible with standalone.
- **The shell (`serve.py`)** now exposes a tiny **cross-module bus**
  `window.LifeOS = { show, goToEdit }` in the composed router script. This is the
  seam the next threads hang off.
- Clean trick: the "clear on manual chip click" listener checks `e.isTrusted`, so
  the programmatic chip click from goToEdit does NOT wipe the banner it just set.
- **Model is NOT in this path** — pure data-matching (title -> occasion ->
  existing per-card data-occ), per the README "keep the heavy model out of the
  hot path". No shared JSON store needed yet (occasion inferred at render time).

## Run / test
`python3 projects/life-os/serve.py` (port 8800; preview server name `life-os`).
Gated by THEDAY_KEY (day-planner/.env) — open `/?k=<key>` once to set the cookie.
NOTE: serve.py loads _ROUTER_JS as a module constant at process start, so after
editing serve.py you must RESTART the process (planner/feed html are re-read per
request, but serve.py constants are not). Currently running as the preview
process; Annabel has it open in her browser.
