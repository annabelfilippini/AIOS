**How to read this:**
- **Tom's vault** is the source of truth for canon + personal context. He writes Obsidian, never types into Supabase directly.
- **Granola Seat B** (exec) lives only on Tom's laptop, transcripts stay in vault, never reach Supabase. This is where Tom + Josh have any conversation that touches Peter, Erica, or any other employee by name.
- **Granola Seat A** (operational) is shared by people who run prospect/client calls. Transcripts auto-flow to Supabase but land as `status='pending'` until Tom or Josh approves.
- **Cloudflare workers** are the always-on plumbing. The vault-sync worker is the new piece — it reads allowlisted folders from a private GitHub mirror of Tom's vault and upserts them to Supabase.
- **Supabase** holds everything operational. Every row has a visibility scope. Every read is gated by RLS against the requester's personal JWT.
- **Each person's Cowork** uses *their* JWT, not a shared admin key. The service-role key only lives in Cloudflare workers.

## Access model (the new piece — read this carefully)

Three layers of separation, in increasing strength:

### Layer 1 — Source separation (strongest wall)

What's not connected can't leak.

| What | Where it lives | Connected to Supabase? |
|---|---|---|
| Tom's exec calls with Josh | Granola Seat B → Tom's vault only | **No** |
| Tom's personal Gmail | Tom's laptop only | **No** |
| Tom's `aios-audit/_run/` notes | Tom's vault only | **No** |
| Operational sales/client calls | Granola Seat A | Yes, via ingest worker |
| Company Gmail | Company Workspace | Yes, via ingest worker |
| Canon files | Tom's vault | Yes, via vault-sync worker (allowlisted folders only) |

### Layer 2 — Approval queue (humans gate operational data)

Every operational call lands in Supabase with `status='pending'`. Only `founder` role (Tom, Josh) sees pending rows. They review and tag:

- `approved + company` — visible to everyone scoped to that company
- `approved + team_marketing` — only Erica's role sees it
- `approved + team_ops` — only Peter's role sees it
- `private` — row gets deleted (call belongs in vault, not Supabase)
- `rejected` — soft-delete with reason

This means a Granola call that *accidentally* contains exec-only content (e.g. Tom and Josh on the line for a "client call" that drifts into personnel) gets caught before any employee sees it.

### Layer 3 — Row-level security (database enforces scope)

Every employee has their own Supabase Auth user → their own JWT → their own role claim. RLS policies on every table filter rows by role and scope. The database refuses unauthorized reads; the app can't bypass it.

**Roles defined:**

| Role | Who | Reads |
|---|---|---|
| `founder` | Tom, Josh | Everything across all 4 companies. Approval rights. |
| `dri_marketing_sales` | Erica | Pilot company only. Approved company-wide + her own + visibility='team_marketing'. |
| `dri_operations` | Peter | Pilot company only. Approved company-wide + his own + visibility='team_ops'. |
| `viewer` (future) | Limited contractors | Approved company-wide only. |

**Critical rule:** no human runs the Supabase `service_role` key in Cowork. That key lives only in Cloudflare workers (server-side ingest jobs). Anyone with `service_role` bypasses RLS entirely.

## Vault → Supabase sync (so Tom never copy-pastes)

Tom writes in Obsidian. Two folders auto-sync; everything else stays vault-only.

**Sync source:** Obsidian Git plugin pushes Tom's vault to a private GitHub repo every commit (or every N minutes on auto-commit). A Cloudflare cron worker pulls from GitHub every 10 minutes, walks the allowlist, upserts changed files into `canon_docs`.

**Allowlist:**

| Path pattern | Synced to | Visibility |
|---|---|---|
| `canon/<co>/_normalized/*.md` | `canon_docs` | `company` (employees scoped to `<co>` can read) |
| `canon/<co>/decisions/*.md` | `canon_docs` | `founder` (Tom + Josh only) |

**Not synced (vault-only forever):**

- `aios-audit/_run/*` (operator notes)
- `aios-audit/tom-context.md` (Tom's personal map)
- `aios-audit/_drafts/*` (Tom's scratch)
- Any folder not on the allowlist

**The user-facing rule:** to share a doc with Josh, Tom moves it into `canon/<co>/decisions/`. To make something company-wide, he moves it into `canon/<co>/_normalized/`. To keep it private, he leaves it anywhere else.

## What could go wrong (updated)

Same five from v1, plus three new ones:

6. **Tom forgets to use Seat B for exec calls.** Mitigation: Seat B's Granola is configured as the *default* on Tom's laptop. Seat A is opt-in (he picks it when joining a sales call). The default-safe direction.

8. **RLS policy bug leaks data to wrong role.** Mitigation: every new table gets a default-deny RLS policy *first*. Write test queries with each role's JWT before adding rows. The `schema-v1.sql` file includes these tests.
